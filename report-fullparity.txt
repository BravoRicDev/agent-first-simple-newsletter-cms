PARTE B — customFields in scrittura con doppio id (ghl_id + external_id)
================================================================================
Stato: IMPLEMENTATA, TESTATA, FUNZIONANTE

Contesto:
  Il cliente ha verificato che il bug dei customFields (id=UUID interno invece
  di ghl_id reale) era gia' corretto in LETTURA dalla PARTE A, ma in SCRITTURA
  (createContact/updateContact) il merge dei customFields in ingresso funzionava
  SOLO per "cf.key" (field_key umano interno): mergeData[cf.key] = cf.field_value.
  Un payload in formato GHL reale ({id: <ghl_id>, value: "..."}) senza "key"
  veniva silenziosamente ignorato (if (cf.key) ...).

Implementazione effettuata:

  1) Nuova funzione: async resolveCustomFieldKey(siteId, idOrKey)
     (src/services/contacts-clone.js, linea 51)
     Query su custom_fields WHERE site_id=$1 AND object_key='contact' AND active=true
     AND (ghl_id=$2 OR external_id::text=$2 OR field_key=$2).
     Ritorna field_key se trovato, altrimenti null.
     Supporta tutti e 3 i formati: ghl_id, external_id (UUID), field_key.

  2) Aggiornata logica merge in createContact (linea 238-266):
     Per ogni cf in data.customFields:
     - Se cf.id presente (formato GHL): risolve via resolveCustomFieldKey(siteId, cf.id)
     - Se non risolto e cf.key presente (retrocompatibilita'): risolve via resolveCustomFieldKey(siteId, cf.key)
     - Se risolto: mergeData[fieldKey] = cf.value ?? cf.field_value ?? ""
     - Se non risolto nulla: console.warn + ignora entry (non rompe la scrittura)

  3) Aggiornata logica merge in updateContact (linea 332-360):
     Stessa logica identica a createContact (codice speculare).

  4) Verifica lettura (PARTE A):
     buildCustomFields (linea 64) espone { id: def.ghl_id || def.external_id, value: v }
     serializeContactSearch usa buildCustomFields — confermato.

  5) Nuovo test: test/clone-parity/contacts.test.js
     "Parity ghl_id: round-trip customFields GHL reale in scrittura e lettura"
     - Crea contatto, definisce custom field con ghl_id reale
     - PUT con formato GHL: { id: <ghl_id>, value: "Organico" }
     - GET e verifica: customFields[0].id == ghl_id, customFields[0].value == "Organico"
     - Test anche con UUID interno (external_id): stessa logica, valore salvato e riletto

Layer NON toccato:
  - src/services/custom-values.js: getCustomValues/setCustomValues/mergeCustomValues
    lavorano su un oggetto JS { field_key: value, ... } persistito come JSONB in
    contact_custom_values.values — layer corretto cosi' com'e'.
