ROUND 13 — COMMERCE (products/invoices)
  Bug: i serializer esponevano SOLO l'UUID interno (external_id); un id reale
  GHL (ghl_id, ~20 char alfanumerici) in input GET/PUT/DELETE/filtro non
  risolveva mai. Cursore di paginazione invoices non site-scoped (lookup
  globale => rischio cross-tenant su siti gemelli).
  Fix applicati:
   - src/services/products-clone.js
       * import findByAnyId/publicId (rimosso ensureExternalId/findByExternalId)
       * serializeProduct/serializePrice: id = publicId(row) (ghl_id preferito)
       * cursore startAfterId: lookup site-scoped
         (external_id::text = $2 OR ghl_id = $2) — prima globale
       * getProduct/updateProduct/deleteProduct: findByExternalId -> findByAnyId
       * rimossi ensureExternalId "lazy" su insert (external_id ha gia
         DEFAULT gen_random_uuid() in db/088, RETURNING * lo popola)
   - src/services/invoices-clone.js
       * id e item.id via publicId
       * nuova contactPublicId(): contactId in output = ghl_id reale del contatto
       * filtro ?contactId= e create: accettano UUID O ghl_id, site-scoped
       * cursore invoices: ora site-scoped (prima lookup GLOBALE — bug scoping)
       * rimossi ensureExternalId lazy (invoices/invoice_items)
   - src/routes/api-clone/products.js : requireUuid -> requireAnyId (3 route :id)
   - src/routes/api-clone/invoices.js : requireUuid -> requireAnyId (3 route :id)

       * nextStartAfterId: esposto nello stesso formato id dei messaggi
         (source_message_id reale, fallback UUID) — riutilizzabile com'e.
  Bug (memberships): POST /memberships/:id/enroll accettava contactId solo UUID;
  contactId in output era UUID. Fix:
   - src/routes/api-clone/memberships.js
       * nuova contactPublicId() (ghl_id reale, fallback UUID) usata in
         create/list/update enrollment
       * validazione contatto: findByExternalId -> findByAnyId (accetta ghl_id)
       * (memberships/courses/enrollments restano UUID-only: colonne ghl_id
         ASSenti — verificato schema, no-op corretto, non omissione)

ROUND 15 — LOCATIONS
  Bug REALE (crash): getLocationByIdOrExternalId confrontava la colonna UUID
  external_id = $1 con un id non-UUID (stile GHL) => PostgreSQL errore 22P02
  "invalid input syntax for type uuid" => 500 Internal Server Error su
  GET /locations/{ghlId} invece di 200. Inoltre PUT business-info usava
  findByExternalId("sites") => 404 silenzioso sul ghl_id reale.
  Fix:
   - src/services/agency-clone.js
       * serializeLocation() unificato: id/locationId = location_external_id
         (fallback external_id)
       * getLocationByIdOrExternalId: confronto
         `external_id::text = $1 OR location_external_id = $1` (cast ::text
         evita 22P02, accetta entrambi i formati, niente crash)
       * nuova resolveSiteInternalId(identifier): risolve UUID interno O
         location_external_id (usata dal PUT business-info)
   - src/routes/api-clone/users.js
       * PUT /locations/:id/business-info: findByExternalId("sites") ->
         resolveSiteInternalId (accetta id GHL reale)
       * import findByExternalId rimosso (non piu usato)
  (teams resta UUID-only: niente colonna ghl_id, no-op documentato)
